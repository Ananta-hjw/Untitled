# 동쪽 고갯길 맵 크기 검토

## 결론

1장보다 넓은 맵을 만들 수 있다. 우선 **4800×3200 월드 좌표**를 권장한다.
이는 제안이며 이번 이미지 작업에서 기존 맵 크기나 게임 연결은 바꾸지 않았다.

| 항목 | 현재 1장 야외 | 동쪽 고갯길 제안 |
| --- | --- | --- |
| 월드 전체 크기 | 3432×2288 | 4800×3200 |
| 가로·세로 비율 | 1 | 약 1.40 |
| 전체 면적 비율 | 1 | 약 1.96 |
| 32단위 길찾기 격자 상한 | 108×72 = 7776칸 | 150×100 = 15000칸 |

현재 크기는 `src/config.ts`의 `2400×1600 × 1.43`에서 계산했다.
실제 통행 가능한 영역은 맵별 다각형과 장애물 때문에 이보다 작다.

## 월드 크기와 그림 해상도

새 바닥 원본은 **1536×1024**이며, 남쪽 들판 원본과 같은 해상도다.
4800×3200에 표시할 수 있지만 이는 3.125배 확대이며 원본 디테일이 증가하지 않는다.
현재 1장 배경은 같은 해상도를 2.234375배로 표시하므로, 새 맵에서 바닥은 더 부드럽게 보인다.
큰 월드와 고해상도 원화는 별개다. 이번 결과를 고해상도 원화라고 간주하지 않는다.

선명도를 더 높이려면 고해상도 원화를 추가 확보하거나, 상세 지면을 구역별로 그린 후
실행 시 여러 텍스처로 나누는 방식을 쓸 수 있다. 사용자에게 보이는 맵은 한 장으로 유지할 수 있다.
단순 이미지 업스케일만으로 세부 묘사가 늘었다고 판단하지 않는다.

1536×1024 RGBA 텍스처의 기본 픽셀 메모리는 약 6 MiB다.
4800×3200을 그대로 텍스처로 쓰면 약 58.6 MiB다. WebP 파일 용량과 GPU 메모리는 다르다.
원본/실행 텍스처의 크기를 월드 좌표와 같게 만들 필요는 없다.
대형 텍스처 사용 전 기기의 `MAX_TEXTURE_SIZE`를 확인하고, 필요하면 2048 이하 청크로 나눈다.
미프맵·렌더 타깃·다른 소품과 드라이버 메모리는 이 계산에 포함하지 않았다.

## 실제 맵 추가 시 필요한 코드 변경

- `src/world/maps.ts`: 새 MapId, 출구, 스폰, 통행 영역과 소품을 정의한다.
  `bounds`는 현재 통행 영역 의미도 있으므로 별도 `artBounds`/월드 외곽을 두는 편이 안전하다.
- `src/world/mapArt.ts`, `src/world/village.ts`: 공통 WORLD_WIDTH/HEIGHT로 배경을
  표시하는 경로를 맵별 외곽 크기를 읽도록 바꾼다.
- `GameScene.setCameraBounds()`: 야외 카메라의 공통 크기를 맵별 외곽으로 바꾼다.
- `src/ui/mapPreview.ts`: 미니맵/지역 지도 범위도 같은 외곽을 사용한다.
  새 소품은 현재 village-props 고정 경로에 별도 텍스처 선택을 추가해야 한다.
- `src/world/navGrid.ts`는 입력 영역 크기로 격자를 만들므로 구조적으로 확장 가능하다.
  격자는 약 1.93배 늘어나며, 실제 소품·적을 배치한 뒤 탐색 비용과 모바일 프레임을 측정한다.
- 기존 MAP_EXPANSION_SCALE을 전역으로 다시 올리지 않는다. 새 고갯길만 넓히고
  캐릭터·소품·기존 실내 크기를 유지한다. 충돌·좌표·화면 가림을 같은 배치 자료로 관리한다.

4800×3200은 코드와 메모리 구조를 검토한 현실적인 시작안이며, 실제 모바일 성능 검증을
완료한 수치는 아니다. 통행 영역, 카메라 가장자리, 절벽 충돌, 쉼터 출입, 지도 표시를
연결한 뒤 브라우저와 Android에서 확인해야 한다.
