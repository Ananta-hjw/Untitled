# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`AGENTS.md` holds the repository's style, testing and commit conventions; follow it. This file adds what you need to work safely in the code.

## Working with the user

- Never commit or push on your own. Always ask the user first, every time. `.claude/settings.json` enforces this with a PreToolUse hook (`.claude/hooks/confirm-git-commit-push.sh`) that forces a permission prompt for `git commit`, `git push` and GitHub MCP file writes.
- The user writes in Korean; reply in Korean. Code comments and README are mostly Korean too.
- Whenever you design or add a character who fights in the game — an ally (companion, fighting NPC) or an enemy of upper rank or above (상급 이상: commanders, bosses, heirs, named rivals) — always recommend a job for it from `src/entities/jobs.ts` / `docs/jobs.md` (base job and likely advancement branch, with a one-line reason tied to its story and fighting style), and note which combat art it would need. Recommend jobs only for characters who need to fight; people who never fight (villagers, shopkeepers, story-only characters) and low/mid-rank minions get none.

## Architecture

**Title screen.** `scenes/TitleScene.ts` (`'title'`) is the first scene: a temporary background (`src/assets/title/background.webp`, a downscaled copy of the Rowen overview art), the title and two buttons. 설정 reuses `PauseMenu.openSettings()` (settings view only; 돌아가기 closes) and saves to the same settings key. 시작하기 fades the camera out over `TITLE_FADE_MS` and starts `'game'` with `{ fromTitle: true }`, which makes `GameScene.create()` fade in over the same time (the flag is cleared from the data after use). In dev builds a `?map=` URL skips the title (`main.ts`), which the browser tests rely on; the last browser test covers the title flow.

**Opening.** A new game started from the title (no progress, no quests, `untitled-rpg.opening` not `'seen'`; `shouldPlayOpening()` in the pure `story/opening.ts`, `tools/opening.test.mjs`) plays a short scripted story on `village-north` before the player gets control: the day before the harvest festival, Sion meets Serena, Herman, Sia and Linea and hears that Ruan is waiting at the training hall (about 2 minutes). The script is the `OPENING` step list (`OpeningStep`: caption, hero path, NPC place/walk/face, dialogue, outro, plus camera pans, head emotes and scene `cue`s used by the festival); `scenes/OpeningDirector.ts` runs it on the game clock, drives the hero through `readInput()` (`openingInput`, at `OPENING_WALK_SCALE`) and scripted NPCs through `Npc.placeAt`/`walkTo`/`faceTowards`/`release`, and draws the letterbox bars, captions and the 건너뛰기 button. During it the HUD and buttons are hidden and attack, dodge, parry, talk, pause, map and character panel are blocked; the skip button, Esc and the Android back button skip. `finishOpening()` releases the NPCs, saves `'seen'`, restores the UI and shows `OPENING_HINT`. In dev builds `?opening` forces it (the browser test uses it).

**Harvest festival (chapter 1).** Confirming 축제 전야 with Rosetta (`festival-eve` done → chapter phase `raid`, `village-raid` auto-starts) writes `'pending'` under `untitled-rpg.festival` and travels to the square; entering `village` with that flag while the raid has not started (`shouldPlayFestival()` in the pure `story/festival.ts`, `tools/festival.test.mjs`) plays a second scripted cutscene of about 3 minutes with the same director (`startCutscene()`): all eleven villagers at feast seats around a bonfire (`festivalNpcs()`, shopkeepers come out, patrol guards are left out), Herman's toast, family, Ruan, Vernel and Eila, Teon at the gate, sky lanterns, a cold wind, the alarm, three trackers walking in through the south gate, the villagers fleeing up the north road (Herman opens his house and the clinic; the inn and smithy are too close to the gate) while Serena and Eila stay to guide people and tend the wounded, Sia and Linea running north, and Sion and Ruan drawing swords, ending on the caption 꺼져 가는 등불. `scenes/FestivalStage.ts` draws the bonfire, feast tables, lantern strings, sky lanterns and the wind/alarm overlays on the game clock (cues `cheer`, `lanterns`, `wind`, `alarm`; `raiders` is handled by the scene). While it plays `syncRaidEnemies()` spawns nothing, quest markers are hidden and the cutscene's raiders (`festivalRaiders`, `FESTIVAL_RAIDERS` paths over `RAIDER_ENTRY_MS`) are plain `Enemy` objects outside `this.enemies`, so they never fight. When it ends or is skipped, `finishFestival()` saves `'seen'` and `travel()`s to the square at the hero's position, which rebuilds it in the normal raid state with the first wave. The festival-eve dialogue itself is now only Rosetta calling everyone out. In dev builds `?festival` forces it when the saved quests are at the start of the raid.

**One scene, one clock.** `scenes/GameScene.ts` runs a whole session. All gameplay timing uses the scene's own `now` (ms), advanced in `update()` by `min(delta, 50)`. Attack timing, combos, dodge, invulnerability, respawns and effects all compare against it. Do not use `this.time.delayedCall` or `Date.now()` for gameplay; they drift from the game clock when frames drop. Per-run state is reset in `resetState()` from `init()`, because class field initialisers run only once and the scene must survive `scene.restart()`.

**Frame-rate independent motion.** Lunges and dodges are not speed × dt. They move by the change in an integrated progress curve (`entities/movement.ts`), so the distance is identical at any frame rate. Tests assert this at 20/30/60/120 fps. Keep new displacements in that form.

**Characters.** `entities/Character.ts` is a container whose position is the feet and whose depth is its y (y-sorting). Its body is either a Phaser `Sprite` (the slimes, from code-drawn textures in `world/placeholderArt.ts`) or a `HeroSprite` (the player). Both are driven by animation keys named `${key}-idle`, `${key}-walk`, `${key}-attack1..3` and `${key}-dodge`.

**The hero.** `entities/HeroSprite.ts` shows whole-character frames from `src/assets/hero/academy/*.png`. `entities/heroFrames.ts` is the pure part: it picks one of 8 facings from actual displacement (with hysteresis), maps attacks to the 6 non-vertical attack facings, and decides which frame is shown at each ms of an action. `HeroSprite.advance(ms)` is called by the scene with the game step (not real time), so its frames slow down, stop for hit stop and freeze while paused in step with the hit timing; driving it on real time makes attacks started during slow motion finish before their hit window and miss. Frame rectangles plus foot and blade anchors live in `frames.json`, generated by `tools/build_hero_frames.py` (`ANCHORS`, `DIAGONAL_ATTACK_ANCHORS`). The source sheets are never edited. The game draws the weaponless `unarmed/*.webp` sheets (the sword is a separate layer placed by `entities/weaponPose.ts`), while the anchors were measured on the armed sheets: the script moves the four-way walk poses by `UNARMED_WALK_SHIFT` (the unarmed poses sit up to 46 px further left) and widens every rectangle to all visible pixels of the unarmed cell (`fit_to_unarmed`), so no frame is cropped; `weaponPose.ts`'s `WALK` scabbard points carry the same shift.

**Hits come from the drawn blade.** `HeroSprite.getBlade()` returns the guard and tip in world space for the current frame. `GameScene.updateAttackTrace` sweeps the blade between frames and tests it against each enemy with `combat/blade.ts` (`bladeHitsEllipse`, `clipBladeSweep`), inside a ground-plane lane from `insideAttackLane`. The trail effect uses the same blade positions, so what you see is what hits. Because each attack has only four drawn poses, the moment the strike pose appears (`strikePoseStart()` in `heroFrames.ts`) `CombatEffects.slash()` fills the jump from the previous pose's blade to the strike pose's blade with a tapered crescent (tip rotating around the guard, through the front side; a light streak for the thrust), which grows in `SLASH_GROW_MS`, holds and fades on the game clock in the same pooled Graphics; it is visual only. The side (left/right), front (down) and rear (up) attacks (all three combo stages) use six-pose sheets (`attack-six/`, `tools/build_attack_six.py`, `SIDE_SIX`/`FRONT_SIX`/`BACK_SIX` in `heroFrames.ts`): the body comes from the sword-removed edit and each frame's guard and tip were measured on the armed source (the bodies match pixel for pixel; the front and rear blades are lengthened to the side length, the front thrust uses the `down` perspective weapon and the rear thrust the `up` one; rear attack weapons are drawn behind the body), so the weapon layer is placed like any other frame. The one exception to "what you see is what hits": a front (down) attack also hits enemies inside the attack lane within `PLAYER.frontReach` ground distance during the hit window (`insideFrontReach`), because a blade swung toward the viewer is drawn foreshortened. Three timings must agree: each combo stage's `hitDelayMs`/`intervalMs` in `config.ts`, the pose start times in `heroFrames.ts` (`POSE_STARTS`, `ACTION_DURATION`), and the drawn strike frame. `tools/hero-sprite.test.mjs` checks that.

**World and maps.** `world/maps.ts` (pure) lists the maps: the village in two maps joined by a centre road (`VILLAGE_LINK`) — 로웬 마을 북쪽 (`village-north`, the houses: Sion's, the chief's, the clinic and Linea's; `START_MAP`, spawn at Sion's door) and the square 로웬 마을 (`village`, training hall, shops, inn, south gate and the exits to the hunting grounds), neither with enemies — and the hunting grounds `south-field`, `west-forest`, `east-stream`, each with bounds, props, enemy spawns, interactables and exits. An exit is a zone at the walkable edge plus the arrival point in the target map; `tools/maps.test.mjs` checks that every exit has a way back, arrivals are walkable and outside exit zones, and spawns, exits and enemies are reachable; arrivals (exits, building doors and interior exits) also lie outside every 들어가기/나가기 spot so a held button does not bounce the hero straight back (`arrivalOf()` is 120 px inside the room door, leaving a building puts the hero 80 px in front of its door), clear of the gate sentries, and the south field's way back lands inside the square past the south gate arch so the arch art does not hide the hero. When the player's feet enter an exit zone, `GameScene.travel()` sets `traveling` (which makes `update()` return early), fades the camera out and calls `scene.restart({ map, at, hp })`. `init(data)` picks the map from that data, then `?map=` in dev builds, then the current map, so a plain `restart()` stays on the same map; the carried `hp` is cleared from the data after use. Level and XP need no carrying because they are saved. `world/village.ts` `buildMap()` draws any map: the shared ground texture (tinted per map), props, the map's buildings (each Rowen building has an `area` naming its village map, `buildingsIn(area)`; Linea's cottage comes from `linea-house.png`, with their names above the roof), the code-drawn stream and the exit labels. The hunting grounds reuse the village ground and props until they get their own art. `villageLayout.ts` holds the Rowen village layout (`BUILDINGS` with area, wall footprints and doors, `PROPS` for the square and `NORTH_PROPS`, `areaObstacles(area)`, the south gate passage); village art and measured frames live in `src/assets/village/`. The game loads small WebP copies made by `tools/build_rowen_assets.py` (buildings sheet, per-character `dialogue-768` and `walk_*-60`), never the multi-MB source PNGs; rerun it when the source art changes. The browser test loads the south field by default (`load(map)`), and a village map only for village tests. NPCs outside have an optional `area` (default the square); `regionOf` maps `village-north` to the village region on the world map. `WalkArea` uses rectangular building walls and ellipse obstacles for trunks/rocks, and divides movement into short steps to prevent dodge tunnelling. Draw depth follows the ground contact Y. Building walls come from `body()` in `villageLayout.ts`: they reach `FRONT` px below the art's bottom and `SIDE` px past its sides, so a character approaching from the front or side is always drawn in front of the art (feet below the art's bottom); the north map's top-row buildings' walls reach `WALK_BOUNDS.top` so there is no hidden pocket behind them; Characters behind other buildings or tree canopies are simply hidden by the art (no silhouette, by the user's choice). `world/navGrid.ts` is one shared flow field toward the player; it is recomputed only when the player changes cell, and enemies use it only when the straight line is blocked.

**Building interiors.** `world/interiors.ts` (pure, `tools/interiors.test.mjs`) lists one room per Rowen building except the south gate: size, floor and wall colours, and furniture placed in room coordinates (`(x, y)` is the front-centre on the floor, occupying `w × d`; rugs are walkable). Furniture and floors are measured on the interior artwork in `INTERIOR_ART` (pixel coordinates; `walk` is the floor polygon, narrower at the back like the art, so the back corners' windows and walls are not walkable; `shop` places a shopkeeper, e.g. Merina just behind the counter so it hides her legs). `maps.ts` turns each into a map `in-<id>` (bounds = room centred on `ROOM_CENTER`, `walkPolygon` from `interiorWalkPolygon()`, furniture obstacles, no walk-out exits) with one `exit-<id>` interactable at the door whose `enter` leads back to the building's `door`, and adds a door interactable per building to the village with `enter: { to, at, label }`. Near a village door the talk button reads 들어가기 and the marker shows the building name; inside, near the door it reads 나가기 (marker ▼ 나가기), so walking past the door never leaves; pressing it calls `travel()` like an exit. Shopkeepers may stand inside furniture (behind a counter); only their talk spot must be walkable. Each furniture piece is a rectangular crop of the flat artwork (`Furniture.art`, background pieces from `interiorLayers.ts` fill the rest), so it is opaque floor around the object: `drawInterior()` depth-sorts it by the footprint's back edge, not its front, so people standing beside a piece are drawn in front of it and only people really behind it are covered; keep `art` crops tight (the shop counters stop at the counter top so the shopkeeper's body shows). Foreground strips (`INTERIOR_ART.foreground`, e.g. a counter's top and front, plus the front sill beside the door) are drawn over characters at their bottom edge's depth with `setCrop` on the whole artwork: they must use the `'__BASE'` frame, because the first frame added for a cut piece becomes the texture's default frame and the crop then came out empty, so Merina appeared to stand through her counter. Transparent cut-outs per object would remove the remaining rectangle edges. `world/interiorArt.ts` draws the room in code (planks, back wall with windows, side walls, a front sill drawn in front of characters with the door gap, furniture y-sorted by its front edge); replace it when interior art exists. `setCameraBounds()` limits the camera to the room and widens the bounds to the viewport when the room is smaller, so it stays centred; the minimap draws the floor and furniture for interiors.

**Village people.** `world/npcs.ts` (pure) lists the eleven NPCs (name, spot, height, dialogue id, `shop`, `wander` radius) and the wander rules (`pickWanderTarget`, `direction8`); `tools/npcs.test.mjs` checks it. `entities/Npc.ts` draws one from its 8-direction walk sheets (`walk_frames.json` × 0.6, found with `import.meta.glob`). Shopkeepers (Doran, Merina, Rosetta) stand inside their shops (`inside: InteriorId`, placed with `inRoom()`), have no `wander` and never walk, but turn to face the player; `talkOffset` moves their talk spot in front of the counter. The healer Eila lives inside the clinic during the day (`inside: 'clinic'`, a small `wander`, not a shop); `chapterNpcs()` moves her to the square during the raid and beside Linea's house in the north map afterwards, and after her normal lines in the clinic a `StoryChoice` offers the same heal as the clinic bed. Door markers ask `chapterNpcs()` who is inside now. Each map's `npcs` is filtered by `inside`. In the village, `doorMarkers` show the best quest marker of the people inside above a shop door (and on the minimap). Everyone else walks. Villagers roam the whole map (`roamsFreely`): after a rest each picks a reachable point up to `NPC_ROAM_HOP` from where it stands (`pickRoamTarget`, never inside an exit zone — the scene passes `npcCanStand`), so over time they spread across the map instead of circling their spot; patrol guards keep circling theirs (`pickWanderTarget` within `wander`). Walking NPCs do not stop for the player; only talking to one (`openDialogue` → `Npc.talkedTo`) stops it and turns it toward the player for `NPC_TALK_PAUSE_MS` of game time (the clock is frozen during the dialogue), after which it walks on. Shopkeepers likewise face their default way until talked to. Walk frames advance by distance walked (`walkPose`, `NPC_STEP_RATIO` of the height per step), not by time, so feet do not slide; the hero's walk animation speed is likewise scaled by actual speed over `HERO_WALK_NATURAL_SPEED`. Each NPC owns an `Interactable` (`spot`) that follows it; the scene merges those with the map's interactables in `this.interactables`. NPCs do not collide with the player. Portraits for each NPC are registered in `DialogueBox.ts` under the NPC id, and each NPC's lines use its name as the speaker. A stress mode (pause menu button cycling `STRESS_STEPS` 0/50/100/200, or `?stress=N`) adds `stressNpcs()` copies that reuse the eleven walk sheets and shows `ui/PerfOverlay.ts` (FPS, longest frame, NPC count, texture-memory estimate, JS heap); `stressCount` is a scene field that survives restarts, and choosing a step restarts in the village.

**Companion (동료).** A companion follows the hero and fights on its own; the player never controls it (pure `entities/companion.ts`, `tools/companion.test.mjs`). `GameScene.setCompanion(id | undefined)` sets or dismisses it and saves it under `untitled-rpg.companion`, so it comes along across `travel()` and relaunches (`loadCompanion()` in `create()`; in dev builds `?companion=joan` / `?companion=none`). It is an `Npc` built from `companionNpcDef()` with `setBattle(true)`, kept outside `this.npcs` (no talk spot, quest marker, raid placement or arena handling) and driven by `updateCompanion()`: when an enemy that `canEngage()` (alive, not a boss, within `COMPANION.leash` of the hero) is within `NPC_COMBAT.engageRadius` it uses the defenders' `NpcFighter` through `Npc.updateCombat`, hitting through the shared `allyStrike()` with `companionDamage()` (a fraction of the hero's damage); otherwise `Npc.followHero()` walks or runs after the hero by `followPlan()` and warps behind the hero (`companionSpot()`) when too far. Enemies can target it (`defenderTarget()`, and `onEnemyStrike` lets it take a strike aimed past the hero via `companionFighters()`). At 0 HP it kneels (`downed`) and `revive()`s after `COMPANION.recoverMs`, so it never needs protecting. A parry or just dodge calls `focusCompanion()`: for `focusMs` it targets only that enemy and hits it × `staggerBonus`. It is hidden while a cutscene plays or the boss arena is up. The only companion so far is 조안 (chapter 2 draft), drawn with Teon's sprites until her art exists (`COMPANIONS.joan.skin`).

**Jobs (draft, not wired in).** The pure `entities/jobs.ts` (`tools/jobs.test.mjs`, design in `docs/jobs.md`) defines eight base jobs (검사, 기사, 궁수, 법사, 도적, 클레릭, 창술사, 음유시인), each with two first-advancement branches (`JOB_ADVANCE.firstAdvanceLevel`) and one second advancement per branch (`secondAdvanceLevel`), each needing the level and a planned trial quest (`advanceBlock`). Sion stays in the sword line (`HERO_JOB_ROOT`); other lines are companions' (`COMPANION_JOBS`, Joan is a lancer). `jobStatBonus()` sums the stats along the path, meant to be added to `totalStats` like gear; `parseHeroJob()` reads `untitled-rpg.job`. Nothing in the scene uses it yet.

**Quests and minimap.** `story/quests.ts` (pure, tested by `tools/quests.test.mjs`) defines the quests (giver NPC, optional prerequisite, one objective counting a `QuestEvent`: kill in a map or anywhere, combo finisher, or talking to an NPC), the state machine (`talkTo`, `recordEvent`, `markerFor` → `new`/`ready` for main quests (yellow), `sub-new`/`sub-ready` for side quests (green), `progress`/`target`; `MARKER_PRIORITY` orders them when several apply, e.g. on a shop door) and the save format under `untitled-rpg.quests` (separate from progress, invalid entries dropped per quest). The scene keeps `quests`, asks `talkTo()` first when the player talks to an NPC (falling back to the NPC's normal lines), fires `questEvent()` on kills and when a third combo stage starts, and calls `refreshQuests()` to update the head markers (`Npc.setQuestMarker`, styles in `MARKER_STYLE`) and `ui/QuestTracker.ts`. Rewards are XP plus optional `rewardGold`/`rewardItems`. `ui/Minimap.ts` draws a player-centred circular map into a canvas texture every 100 ms of real time (ground, props and buildings from the same atlases, exits, NPC and enemy dots, quest markers clamped to the rim when out of view); the scene passes a collector that is only called on redraw. Both are scene fields cleared in `resetState()` and rebuilt in `create()`. Tapping the minimap (or M) opens `ui/WorldMap.ts`, a full-map overlay built from the pure `world/worldMap.ts` (`REGIONS` on a grid, `ROUTES`, `regionOf` maps interiors to the village, visited regions saved under `untitled-rpg.visited`; `tools/world-map.test.mjs` checks routes match real exits). Unvisited regions and regions without a map show '?'; the world map shows no quest markers; while it is open `update()` returns early like the item panel.

**Combat guide (early tutorial).** The first main quests teach one combat basic each, from a fitting person: `ruan-training` (attack, three finishers), `ruan-dodge` (three dodges), `ruan-parry` (two parries on south-field slimes), then `ruan-field`, `eila-potion` (Ruan sends you to Eila; talk, then use a heal item; reward two potions) and `vernel-resonance` (Eila sends you to Vernel; talk, use 공명, report to Ruan), then `ruan-forest`. They are flagged `tutorial` and count the new `QuestEvent`s `dodge` (`startDodge`), `parry` (parry branch of `onEnemyStrike`), `item` (`useHealItem`) and `resonance` (activation). `parseQuests()` runs `skipPassedTutorials()`, so an old save already past them marks them done instead of dropping a lesson into the middle of a run. The pure `story/tutorial.ts` (`LESSONS`, `activeLesson`, `lessonToShow`, `tools/tutorial.test.mjs`) ties each lesson to its quest step; when one becomes active and has not been seen (`untitled-rpg.guide`), `GameScene.showLessonIfNew()` opens `ui/GuideCard.ts` (전투 가이드 n/5, the teacher, control notes, 확인; the game is frozen while it is open, `menuOpen()`), lowering full HP to 70% for the potion lesson and filling the resonance orbs for the resonance lesson, and `updateGuideHighlight()` pulses a ring around the lesson's button while it is being practised. Browser tests' `load()` marks every lesson seen unless called with `{ guide: true }`.

**Gold and items.** `items/inventory.ts` (pure, `tools/inventory.test.mjs`) defines the items (`ITEMS`: potion, lunch and travel biscuit heal, blue dew restores MP, antidote herb clears the moth/pool slow, slime gel is a sellable material; `itemEffectText()` for the panels), each shop's stock (`SHOP_STOCK`: Merina sells potion and lunch, the chapter-2 peddler Fern sells potion, travel biscuit, blue dew and antidote herb; `buy(..., shop)` refuses another shop's goods), the immutable `Inventory` operations (`addItem`, `canUse`/`useConsumable` (HP, MP, slow), `useItem` (HP only), `bestHealItem`, `buy`, `sell`, `slimeDrop`/`applyDrop`) and the save under `untitled-rpg.inventory`. The scene keeps `inventory`; a kill calls `collectDrop()` (gold and items are picked up at once, shown with `ProgressEffects.showPopup`), quest completion calls `giveRewards()`, the quick item buttons along the bottom edge left of the block button (slot 1 key Q, slot 2 key R) uses the best-fitting heal item with `USE_COOLDOWN_MS` on the game clock, and `ui/ItemPanel.ts` is the bag (from the pause menu) and a shop (`openItemPanel('shop', shopId)`; Merina's opens after her normal dialogue), three rows per page with ◀ ▶ when there are more. `ui/QuickSlotPanel.ts` lays the consumables out side by side as tiles. Items without art in `assets/items/icons.webp` get a drawn placeholder (coloured circle and two letters) appended to the same `item-icons` canvas texture by `registerItemIcons()`, so every screen keeps drawing `(item-icons, id)` and real art replaces it once added to the atlas. Gear has an optional `shop` (`'doran'` by default; the travel cloak is `'fern'`), and `gearForSale(shop)`/`buyGear(..., shop)` keep each shop's gear apart. While the panel is open `update()` returns early like the pause menu, and closing it drains input through `onResume()`.

**Rest points (save where you rested).** `story/restPoints.ts` (pure, `tools/rest-points.test.mjs`) defines the places to rest (chapter 2 adds the mountain-pass shelter, see above): the inn (after Rosetta's normal lines a `StoryChoice` asks 쉬어 가기) and Sion's bed (`HOME_BED_SPOT`, an interactable added in `in-home` whose button reads 쉬기). Resting fills HP and saves the place under `untitled-rpg.rest`; level, quests and items are saved as they change anyway, so only the restart position is stored. `GameScene.init()` uses it only when the scene starts from the title (`fromTitle` without a map); no rest yet means Sion's door. `canRest()` blocks resting during the raid. Death also sends the hero there: every hit that lands is recorded in `damageLog` (the pure `combat/damageLog.ts`, `combat/bossPattern.ts`, `recordDamage`/`deathReport`, `tools/damage-log.test.mjs`; reset on scene start), and `PLAYER.respawnMs` after a death (game clock, so the fall plays) `openDeathPanel()` shows `ui/DeathPanel.ts`: the last blow, each monster (name and level) with hits and damage taken, the total, and where the hero will restart. **Block (parry).** The 막기 button left of and below the attack button (key L; 회피 is in the bottom-right corner) is a parry, not a hold: a press while not attacking or casting opens a `BLOCK.windowMs` window (`parryUntil`) and starts `BLOCK.cooldownMs` (`parryReadyAt`); `blocking` is true only inside the window, movement is slowed to `BLOCK.moveScale` and `drawShield()` draws a shield in front of the hero. A strike from the side the hero faces during the window (`onEnemyStrike`, projectiles judged by their travel direction) is a parry: no damage and no knockback, the attacker is stunned for `BLOCK.stunMs` (`enemy.interrupt`), the next attack within `JUST_DODGE.counterMs` is a counter, the parry cooldown resets at once and the dodge cooldown left drops by `BLOCK.dodgeRefundMs` (1 s, not below zero). A strike from behind or after the window lands normally. The dodge cooldown is `DODGE.cooldownMs` (10 s) × the DEX scale (−0.5% per point, linear).

**Resonance (공명).** Every successful parry adds `RESONANCE.perParry` part to a gauge of `orbs` × `parts` (5 orbs, thirds), counted as an integer in the pure `combat/resonance.ts` (`chargeOnParry`, `orbFill`, `canResonate`, `resonanceTaken`, `tools/resonance.test.mjs`) and saved under `untitled-rpg.resonance`. `Hud.setOrbs()` draws the orbs right of the HP bar (pie-filled by thirds, redrawn only on change). **Frost beetle (chapter 2).** `frost-beetle` (수호·얼음, the mountain pass's monster; it lives on 동쪽 고갯길; in dev builds `?monsters=frost-beetle` also adds three around any map's spawn via `previewMonsters()`) is slow and armoured: `shellBlocks()` in `combat/monsterTypes.ts` (`FROST_SHELL.frontDegrees`) makes a sword or spin hit from inside its frontal arc bounce off (`GameScene.shellBlocked()`: spark and 막힘, no damage, mana or knockback) unless it is a counter after a parry or just dodge, and `MonsterSprite.setMovement()` turns it one 8-direction step per `FROST_SHELL.turnMs` so the hero can get behind it (`facingVector()` gives the facing).

**Enemies.** `combat/Enemy.ts` is a small state machine: wander → chase → windup (telegraph) → strike → recover, timed on the game clock. When the strike lands it records `lastStrikeAt` and calls back into the scene, which decides whether the player is hit (`strikeReaches` in `combat/justDodge.ts`).

**Just dodge.** A dodge started within `JUST_DODGE.windowMs` before a strike lands, from a spot the strike would have reached, is a just dodge (`isJustDodge`, checked against the dodge's start position, once per dodge). It slows the game clock: `update()` multiplies the frame step by `slowMotionScale(...)` for `slowMs` of real time, so enemies, the player and all game timers slow together. It also resets the dodge cooldown, stuns the dodged enemy for `stunMs`, and marks the next attack started within `counterMs` as a counter (`attackTrace.counter`, damage × `counterDamage`).

**Hit stop and hit reaction.** A sword hit, a finisher, a counter and the player getting hurt each set `hitStopLeft` (`HIT_FEEL.*HitStopMs`, real-time ms, longest wins). `update()` computes the step scale with `gameTimeScale(hitStopLeft, slowMotionLeft)` from `combat/hitFeel.ts`; while it is 0 the frame returns early, and pending button/key presses stay queued for the next frame. A hit slime calls `Enemy.onHit(now)`, which flattens it and lets it bounce back on the game clock (`hitSquash`).

**Heavy hits.** Each blade contact is classified by the pure `strikeKind()` in `combat/hitFeel.ts` (counter > finisher > crit > normal; `HIT_FEEL.critChance`/`critDamage`, no crits on counters); the heaviest kind of the swing picks the hit stop, the camera shake (`HIT_FEEL.shake`) and a brief screen tint. `combat/ImpactEffects.ts` draws the contact flash and sparks, a ground shock ring and dust for heavy hits, slide dust under strongly knocked-back characters, dodge dust, and a splatter when a slime dies. Its 120 particle images are created up front and recycled, move on the game clock (so they freeze during hit stop and slow with just-dodge slow motion), and only the screen tint fades in real time.

**Cooldown rings.** `ActionButton.setCooldown()` draws the shrinking ring and seconds from the pure `ui/cooldownDisplay.ts` (`tools/cooldown-display.test.mjs`), which rounds the remaining time to whole ms first: the game clock is a sum of fractional steps, so 5000 ms left can come out as 5000.000000000001 and would otherwise show 6 s.

**Frame-rate cap (heat).** `main.ts` wraps `game.loop.step` so a frame is drawn only when `shouldRunFrame()` (pure `core/frameRate.ts`, `tools/frame-rate.test.mjs`) allows it: `PLAY_FPS` 60 while playing, `IDLE_FPS` 30 while a menu, dialogue, panel or the world map is open (`GameScene.update()` sets `frameRate.fps` each frame), with `FRAME_SLACK` so a slightly early 60 Hz frame is not skipped. The interval is measured with `performance.now()` since the last drawn frame, not against Phaser's `loop.lastTime`: the rAF timestamp can lag the `performance.now()` that `lastTime` starts from, and comparing the two once kept skipping the first frame so the game never started. Skipped refreshes leave Phaser's clock untouched, so the next drawn frame gets the whole elapsed time and gameplay timing is unchanged. Without it 120 Hz phones drew twice as often and heated up. `MainActivity.preferSixtyHertz()` also asks Android for the 60 Hz display mode. Browser tests call `game.step()` directly and are not affected.

**No per-hit allocation.** Damage numbers (`ui/DamageNumbers.ts`, digits drawn once to a texture), blade trails and dodge ghosts (`combat/CombatEffects.ts`) reuse pooled objects. Keep new combat effects pooled; the target is low-end Android.

**Progression.** The scene keeps `progress` (level, xp) and `stats` (max HP and damage for that level) and resets both in `resetState()`. Killing an enemy calls `gainXp()`, which uses the pure `entities/progression.ts` (`addXp`, `statsForLevel`, `xpToNext`); a level-up raises max HP, heals fully, and updates the name label, the HUD XP bar and the pooled effects in `ui/ProgressEffects.ts`. Player damage reads `stats`, not `PLAYER.damageMin/Max` directly. Progress survives death and is saved to `localStorage` (key `untitled-rpg.save`, versioned) on every XP change by `entities/saveData.ts`; `init()` loads it, so restarts and app relaunches continue from it. The storage is passed in, so a blocked or full `localStorage` only disables saving, and a corrupt or out-of-range save is ignored (new game). Bump `SAVE_VERSION` when the saved shape changes. Uninstalling the app clears the save.

**Dialogue.** `world/interactables.ts` lists talkable spots (ground position, reach radius, marker height, dialogue id); `story/dialogues.ts` holds the lines (speaker, text, optional portrait), currently placeholder text until the story is written. When the player stands near a spot and no enemy is chasing or attacking, the scene shows a marker and a 대화 button (keys E/Enter). `ui/DialogueBox.ts` types lines out and advances on any tap, E/Enter or Space/J. While it is open `update()` returns before advancing `now`, so the whole game is frozen; on close the scene clears buffered attack and dodge input so the advancing key does not attack. Portraits are runtime copies (e.g. `assets/hero/dialogue/neutral-768.png`); add new ones to `PORTRAITS` in `DialogueBox.ts` and the `Portrait` type. New NPCs need an entry in `world/npcs.ts`, a dialogue entry, a portrait and their walk sheets plus `walk_frames.json` (`tools/build_npc_frames.py`), with runtime copies made by `tools/build_rowen_assets.py`.

**Combat button layout.** The pure `ui/buttonLayout.ts` (`combatButtonLayout`, `BUTTON_RADIUS`, `tools/button-layout.test.mjs`) places attack, dodge (bottom-right corner), block (left-below attack), the two quick item slots (left of block, side by side along the bottom edge), the 공명 button above them toward the block button, the five skill slots on an arc around the attack button and the talk button (outside the arc, top-left). Distances are measured from the bottom-right corner and multiplied by the button-size setting, and the test checks that no touch circle (1.2 × radius) overlaps and every button stays on screen and clear of the joystick from 4:3 to 2.4:1 (except 4:3 with large buttons, where the bottom item row comes close to the joystick's rest spot). `GameScene.layout()` only applies it. `ActionButton` listens to every scene pointer-down and tests its own circle, so it ignores a press when `hitTestPointer` finds a visible interactive object drawn above it (a window's buttons or full-screen blocker, e.g. 쉬어 가기 over the 공명 button); The combat buttons (attack, dodge, block, 공명, quick items, skills) also take `ignore: ignoreCombatPress`, which drops a press while `menuOpen()` (dialogue included) or when it is the very touch that advanced or closed the dialogue (`dialogueTap`, set in `onDialoguePointer`), since the dialogue advances on any pointer-down and listener order is not fixed; `onResume()`/dialogue close also drain block and resonance presses (`clearQuickItemInput`). The joystick floats: `joystickZone()` is a bottom-left rectangle (from y 220 down, right edge at half the width or 24 px left of the leftmost combat button's touch circle), and `VirtualJoystick` starts wherever a touch lands in it (`joystickCenter()` keeps the pad on screen) and slides back to `JOYSTICK_REST` on release; it ignores touches while `GameScene.menuOpen()` or the opening is active (`canGrab`).

**Pause and settings.** The top-right II button, Esc, the Android back button (`@capacitor/app` `backButton` listener; without it Android would close the app) and the game going hidden all open `ui/PauseMenu.ts`. While it is open `update()` returns before anything else, so the game clock stops; Esc/back steps back (settings → menu → game). On resume the scene drains buffered attack, dodge and talk input. The menu has 계속하기, 설정 and, only on native (`Capacitor.isNativePlatform()`), 게임 종료. 게임 종료 destroys the Phaser game before `App.exitApp()`, and `MainActivity.onDestroy()` destroys the WebView and kills the process when the activity is finishing: `exitApp` only calls `finish()` and Capacitor does not destroy the WebView, so the old game lingered in the process and the next launch stuttered. Settings (button size, joystick size, just-dodge timing) live in the pure `ui/settingsData.ts`, are saved under `untitled-rpg.settings` separately from progress, fall back per field to defaults when invalid, and are applied by `applySettings()` (`ActionButton.setSizeScale`, `VirtualJoystick.setSizeScale`, `justDodgeWindow`). There is deliberately no in-game 'start over' option. After adding a Capacitor plugin, run `npx cap sync android` and commit the regenerated `android/*.gradle` files.

**Tuning** lives in `src/config.ts` (speeds, combo stages, dodge, `JUST_DODGE`, `HIT_FEEL`, enemy ranges, `PROGRESSION` for XP per kill, XP curve and per-level gains). The version shown on screen comes from `package.json` `version` through Vite's `define` (`__APP_VERSION__`).

## Android and CI

Capacitor wraps `dist/` (`capacitor.config.ts`, `android/`). The app is locked to fullscreen landscape with the screen kept on (`MainActivity.java`, `AndroidManifest.xml`). `.github/workflows/android-apk.yml` runs `npm test` and then builds a debug APK on every push to `main` or `claude/**`, uploaded as the run artifact `untitled-rpg-apk`. `setup-java` caches Gradle downloads (`cache: gradle`), because fetching every dependency from Maven Central on each run sometimes failed with 429 Too Many Requests. Actions are pinned to commit hashes. Signing uses the private key from the `ANDROID_KEYSTORE_*` secrets when they are set, and otherwise the public test key `android/app/debug.keystore`, which must not be used for APKs given to other people.
